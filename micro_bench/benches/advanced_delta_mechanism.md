# 历史状态Delta查询机制 (Historical State Delta Query Mechanism)

## 1. 目的

提供一种机制，允许客户端查询任意版本区间 `i` 到 `j` 的累积 `delta` 值（`delta_{i->j}`），从而高效地更新其证明。

## 2. 实现原理

1.  **存储历史Delta**: Issuer 需要存储每个批次产生的 `delta` 值，并将其与对应的版本号（或批次号）关联起来。这形成了一个历史记录，例如：
    `History = { 1: delta_1, 2: delta_2, 3: delta_3, ... k: delta_k, ... }`

2.  **区间Delta计算**: 当系统收到一个 `(i, j)` 区间的查询请求时（其中 `i < j`），它会执行以下操作：
    *   从历史记录中检索出从版本 `i+1` 到 `j` 的所有单个 `delta` 值：`delta_{i+1}, delta_{i+2}, ..., delta_j`。
    *   将这些 `delta` 值累加起来，计算出区间 `delta`：
        `delta_{i->j} = delta_{i+1} + delta_{i+2} + ... + delta_j`。
    *   将计算出的 `delta_{i->j}` 返回给请求方。

## 3. 优势

*   **高效的证明更新**: 对于长时间离线的客户端，当其重新上线时，无需下载并逐个应用所有中间 `delta`。客户端只需请求一次 `delta_{i->j}`，即可通过 `p_new = p_old + delta_{i->j}` 的方式，一次性将其证明从版本 `i` 更新到版本 `j`。这显著减少了客户端的计算和网络开销。
*   **提升用户体验**: 简化了客户端的证明管理流程，尤其是在网络不稳定或长时间离线的情况下。

## 4. 成本与权衡

*   **Issuer 存储成本**: Issuer 必须存储所有历史 `delta` 值。这份历史记录的存储空间会随着系统运行时间（即批次数量）线性增长。
*   **数据可用性与去中心化**: Issuer 的历史 `delta` 存储成为一个关键组件。为了提高系统的鲁棒性和去中心化程度，可以考虑将这份历史记录发布到持久化的、去中心化的存储解决方案（例如 IPFS、Arweave，或作为交易数据发布在区块链上）上，以避免单点故障。
*   **Issuer 计算成本**: 对于每个查询，Issuer 需要执行一系列的 `delta` 累加操作。虽然这些操作通常是高效的（例如，椭圆曲线点加法），但在高并发查询场景下，仍需考虑其计算负载。
