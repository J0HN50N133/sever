# 实验

## 基础方案

现在基于minchash实现一个可撤销的verifiable credential方案。

1. 系统总共有三个角色: client, issuer, blockchain。

2. **Issuer (签发者):**
    * 持有一个 root accumulator，并负责将其摘要通过智能合约形式存储在区块链上。
    * 负责 accumulator 摘要的更新，此更新受区块链TPS限制（实验中通过 `RateLimiter` 模拟）。
    * 接收用户请求，发放 credential，并将 credential 积累到 accumulator 内，同时发放相应的 proof。
    * 执行 `revoke` 操作来撤销已发放的 credential。
    * 处理核心请求：`add_elements` (添加元素), `remove_elements` (移除元素), `generate_proof` (为特定用户重新生成证明)。
    * 当客户端请求时，为旧版本 proof 重新生成新版本的证明。

3. **Client (客户端):**
    * 向 Issuer 请求 credential。
    * 持有 credential 及其 proof。
    * 调用 `verify_proof` 在链下证明元素属于集合，此操作不受区块链TPS限制。
    * 在验证时，如果发现 proof 版本号不匹配或验证失败，会向 Issuer 请求重新生成新版本的证明。

4. **Blockchain (区块链):**
    * 存储 accumulator 的摘要（digest），通过智能合约进行管理。模拟实验直接存储Hash本体即可，无需存储digest.
    * accumulator 摘要的更新操作受TPS限制。
    * 不直接参与客户端的 `verify_proof` 链下验证过程。
    * 客户可以直接获取到区块链内的accmulator值, 可以认为无TPS限制。

5. **通用机制:**
    * accumulator 每次更新后，版本号会增加。
    * 证明的重新生成是 lazy 的，仅在客户端需要时触发。

## 进阶探索 (Advanced Exploration)

## 批量处理测试 (Batching Test)

### 1. 测试目标

此测试旨在量化“批量处理（Batching）”策略对系统性能和成本的影响。核心目标是验证通过将多个 accumulator 更新打包成单次链上交易，以提高有效吞吐量（TPS）并降低交易成本的可行性。

### 2. 批量处理机制设计

1. **引入增量累加器 (Delta Accumulator)**: Issuer 维护一个临时的 `delta` accumulator。在一个批次处理周期内，所有新的 `add` 和 `remove` 操作都累积到这个 `delta` accumulator 中。
2. **触发条件**: 当满足以下任一条件时，Issuer 会结束当前批次并将变更提交到区块链：
    * **批量大小 (Batch Size)**: `delta` accumulator 中累积的操作数量达到预设阈值 `N`。
    * **时间间隔 (Time Interval)**: 自上次提交以来，经过了预设的时间 `T`。
3. **聚合更新与证明生成**:
    * **链上更新**: 批次结束时，Issuer 将 `delta` accumulator 的值与主累加器 `Acc_old` 合并，得到 `Acc_new = Acc_old + delta`，然后将 `Acc_new` 的摘要作为单次交易提交上链。
    * **新元素证明**: 对于本批次内**新添加**的元素，由 **Issuer 直接计算并提供**其最终的、相对于 `Acc_new` 的完整证明。
    * **旧元素证明更新**: 对于系统中已存在的元素，客户端可以通过获取公开的 `delta` 值，**自行将旧证明 `p_old` 更新为新证明 `p_new`**。

### 3. 测试场景与指标

**场景**:
模拟一个持续的请求流，请求类型按固定比例分配。例如，**75% 的 `add` 请求和 25% 的 `remove` 请求**（通过生成 1-4 的随机数，若为1则为 `remove`，否则为 `add` 来实现）。

**测试变量组**:
我们将测试以下 `批量大小 (N)` 和 `时间间隔 (T)` 的组合：

* **N = 10**，T 分别为 `1s, 5s, 10s`
* **N = 50**，T 分别为 `1s, 5s, 10s`
* **N = 100**，T 分别为 `1s, 5s, 10s`
* **N = 500**，T 分别为 `1s, 5s, 10s`

这将构成 `4 * 3 = 12` 组不同的批量处理策略进行测试。

**核心测量指标**:

1. **有效吞吐量 (Effective TPS)**: 测量在单位时间内，链上实际确认的凭证变更（add/remove）总数。
2. **确认延迟 (Confirmation Latency)**: 测量从单个凭证变更请求被接收，到该变更被包含在一个批次中并最终在链上确认所需的平均时间。
3. **成本节约 (Cost Saving)**: 估算或测量在相同数量的总操作下，批量处理相对于逐个处理所节省的交易费用。

**分析**:

* 绘制“确认延迟”与“批量大小/时间间隔”之间的关系图。
* 分析并寻找一个最佳平衡点，即在可接受的延迟范围内，实现最大化的吞吐量和成本节约。

## Lazy Witness Update 优化实验方案

### 实验背景

基于IMH (Incremental Multiset Hash) 累积器的凭证系统中，传统方案要求所有用户的见证必须与当前最新的累积器根匹配。当系统中有新用户加入时，所有现有用户都需要更新他们的见证，造成巨大的系统开销。

**优化思路**: 利用一个观察，即**添加新元素不会使现有元素的历史见证失效**。用户可以使用旧的见证进行验证，只要验证者确认该用户在旧版本之后没有被撤销即可。

### 核心优化组件

#### 1. LazyVerifier (验证者)
- **本地缓存**: 存储历史版本的累积器根 (version -> root)
- **布隆过滤器撤销检查**: 使用布隆过滤器维护撤销集合，利用其**无假阴性**特性确保安全性
- **智能验证逻辑**:
  1. **优先撤销检查**: 使用布隆过滤器快速判断元素是否被撤销（无假阴性，可能有假阳性）
  2. **本地缓存查找**: 查找客户端见证版本对应的缓存根
  3. **历史根验证**: 使用历史根进行验证，避免不必要的见证更新

**布隆过滤器优势**:
- **安全性保证**: 无假阴性，确保已撤销用户绝对不会通过验证
- **性能优化**: 可能有假阳性，导致一些未撤销用户被要求更新见证，但不影响安全性
- **空间效率**: 相比精确撤销列表，大幅减少内存使用

#### 2. LazyClient (客户端)
- **乐观验证**: 优先使用当前存储的见证进行验证
- **自动更新**: 验证失败时请求新的见证并重试

### 性能指标定义

#### 主要性能指标

1. **吞吐量 (Throughput)**: `ops/sec`
   - 定义: 单位时间内完成的验证次数
   - 计算: `total_operations / total_duration`

2. **平均延迟 (Average Latency)**: `μs`
   - 定义: 单次验证的平均时间开销
   - 计算: `sum(verification_latencies) / count`

3. **最大延迟 (Maximum Latency)**: `μs`
   - 定义: 验证过程中的最大延迟时间
   - 意义: 评估系统最坏情况性能

#### 优化效果指标

4. **缓存命中率 (Cache Hit Rate)**: `%`
   - 定义: 使用缓存历史根成功验证的比例
   - 计算: `cache_hits / total_clients`

5. **更新避免率 (Update Avoidance Rate)**: `%`
   - 定义: 成功使用旧见证避免更新的客户端比例
   - 计算: `accepted_clients / total_clients`

6. **验证成功率 (Verification Success Rate)**: `%`
   - 定义: 验证成功(包括使用缓存和直接验证)的比例
   - 计算: `(accepted_count + rejected_count) / total_clients`

7. **布隆过滤器正检率 (Bloom Filter Positive Rate)**: `%`
   - 定义: 布隆过滤器返回"可能存在"的比例，包括真阳性和假阳性
   - 计算: `positive_checks / total_checks`

8. **布隆过滤器假阳性率 (Bloom Filter False Positive Rate)**: `%`
   - 定义: 未撤销元素被误判为撤销的比例
   - 分析: 与理论预期值对比，评估布隆过滤器实际性能

### 数据分析方法

#### 1. 性能对比分析

##### 与基础方案对比
```
相对性能提升 = (lazy_throughput - basic_throughput) / basic_throughput × 100%
延迟减少比例 = (basic_latency - lazy_latency) / basic_latency × 100%
```

##### 不同场景对比
```
场景间性能差异 = scenario1_metric - scenario2_metric
优化效果稳定性 = std_deviation / mean × 100%
```

#### 2. 参数敏感性分析

##### 缓存大小优化
```python
# 寻找最优缓存大小的启发式方法
def find_optimal_cache_size(cache_sizes, hit_rates, memory_costs):
    efficiency_ratios = [hit_rate / size for hit_rate, size in zip(hit_rates, cache_sizes)]
    # 选择效率比开始下降的缓存大小
    for i in range(1, len(efficiency_ratios)):
        if efficiency_ratios[i] < efficiency_ratios[i-1] * 1.1:  # 10%阈值
            return cache_sizes[i-1]
    return cache_sizes[-1]
```

##### 版本距离影响建模
```python
# 版本距离对缓存命中率的影响模型
def model_cache_hit_rate(version_distance, cache_size, max_version):
    # 简化的LRU缓存命中率模型
    if version_distance <= cache_size:
        return 1.0 - (version_distance - 1) / cache_size
    else:
        return cache_size / version_distance
```

#### 3. 成本效益分析

##### 系统开销节省
```
见证更新节省 = avoided_updates × update_cost
存储开销增加 = cache_size × root_size
净收益 = 更新节省 - 存储开销
```

##### ROI计算
```
ROI = (性能提升价值 - 实现成本) / 实现成本 × 100%
```
